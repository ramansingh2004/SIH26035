# SIH26035 — Verification Plan

Specification Freeze v1 — 2026-09-20. This defines future tests; no application tests or code are generated by the freeze. [DECISIONS.md](../DECISIONS.md) is the architectural oracle. Regulatory expected values require independently verified sources, not circular agreement with an evaluator.

## 1. Layers and environments

Use pure calculation/evaluator/applicability/aggregation tests without HTTP, PostgreSQL, Redis, storage or auth. Separately test service mapping/persistence, real PostgreSQL migrations/repositories, API permissions/schemas, workflow/concurrency, report contexts/rendering, storage/security and performance smoke cases.

Planned tools: pytest, pytest-asyncio, httpx, temporary Docker/testcontainers PostgreSQL and coverage. Mock repositories for isolated services; use real PostgreSQL for NUMERIC, JSONB, CITEXT, partial indexes, transactional locks and concurrent uniqueness. Do not substitute SQLite for those contracts.

Fixtures carry rule/source/edition/verification provenance. Candidate numbers inherited from 02 are isolated synthetic arithmetic fixtures until verified; such tests prove implementation mechanics, not regulatory certification. Test-only fixtures must not be selectable by production sessions/report issue.

## 4. Applicability, rules and schemas

Test an instrument matrix: electronic retail scale, mechanical/non-self-indicating instrument, vehicle scale, software-controlled instrument, Class I, Class III at/below/above candidate endurance capacity, direct-sales and multi-range/multi-interval variants. Unknown feature flags produce REQUIRES_REVIEW, never false/N/A. Optional election changes completion requirements; unelected optional tests remain visible.

Loader tests: valid/invalid YAML, missing class, duplicate keys, overlapping/gapped bands as applicable, unverified provenance, supported-test transitive dependencies, deterministic normalized hash, no active edits, new-version activation, old-session pinning, catalog/checklist immutability and retired historical availability. Activation of unverified required rules fails. Missing-rule evaluation gives REVIEW_REQUIRED/UNDETERMINED and TODO_REGULATORY_VALIDATION IDs.

Observation/context schemas reject extra/invalid fields and incompatible versions; production procedure validation rejects insufficient counts/order/stages. A nonempty-list demonstration is explicitly insufficient. Schema migrations invalidate results and require controlled revision when approved.

## 5. Canonical hash tests

One expected evaluation_input_snapshot includes hash_schema_version, instrument with ranges, test_code, procedure_context, normalized observations, ruleset_configuration_hash, observation_schema_version and engine_version. Golden canonical JSON tests cover key ordering, decimal equivalent spellings/negative zero, exact unit conversion, NFC, UTC timestamp representation, observation/range ordering and meaningful sequence preservation.

Change each semantic field independently and assert input hash changes. Unrelated record IDs/evaluated_at must not change deterministic hashes. Same snapshot/version returns identical deterministic output/result_hash. Result hashing excludes generated IDs/timestamps. Store exact historical input snapshots; old hash reproducibility does not depend on current editable sources.

## 6. Status and outcome tests

Test independent axes: TESTING/COMPLETE/NONCOMPLIANT; UNDER_REVIEW/COMPLETE/NONCOMPLIANT; APPROVED/COMPLETE/NONCOMPLIANT; REPORT_ISSUED/COMPLETE/NONCOMPLIANT are valid states at appropriate lifecycle points. Workflow approval never changes outcome.

Aggregation tests cover precedence STALE > REVIEW_REQUIRED > INCOMPLETE > IN_PROGRESS > NOT_STARTED > COMPLETE; mixed complete/unstarted work is IN_PROGRESS. A current known failed required result yields NONCOMPLIANT even with other incomplete work, but official gates remain closed. Without a known failure, unfinished/unknown required work is UNDETERMINED. Entirely N/A section is COMPLETE/NOT_APPLICABLE; all-N/A/empty session cannot issue. Optional unelected failures are disclosed without silently becoming required aggregate failures. Required construction conformance/checklist results participate correctly.

## 7. Versioned results, retests and review invalidation

- Same current canonical input reuses its result; changed input creates a new evaluation_version.
- Observation/context/environment/equipment/snapshot changes increment relevant revisions, append stale events, clear pointers and invalidate dependent review approvals.
- Immutable prior outputs/input snapshots survive draft source edits/deletes.
- A new retest does not auto-replace an authoritative attempt; explicit selected-run event/reason is required.
- Earlier failed attempts remain in history and report context; verified retest substitution policy is required.
- New selected result/attempt changes regulatory_revision and invalidates old technical approval.
- Approved/issued sources cannot be reevaluated or changed in place; child revision resets current assessments/reviews.

## 8. PostgreSQL and migration integrity

Test clean Alembic upgrade and applicable previous-version upgrades; rollback behavior for partial transactions. Test UUID assignments with GLOBAL null/LABORATORY non-null constraints and active partial uniqueness, refresh successor uniqueness, ownership composite constraints, exactly 17 transactional section creation, immutable result uniqueness by run/version, and one current issued report per series.

Create manufacturer/instrument/ranges/catalog/session/requirements/runs/observations/results and assert joins/snapshots. Cross-lab manufacturer/equipment/attachment/report predecessor references fail. Checklist and construction initializers are idempotent for existing preapproval sessions and refuse approved mutation. Master edits leave session/report snapshots unchanged.

## 9. Concurrency and retry tests

Use real concurrent PostgreSQL transactions for two edits with the same ETag, edit versus approval, result calculation versus source edit, selected retest versus review, rule activation race, numbering allocation and competing report revisions/issues. Expect 428 missing If-Match, 412 stale version, 409 forbidden state/source race, with no partial regulatory/audit commits.

Every regulatory write serializes on parent session; child ETag correctness alone cannot bypass approval locking. Exact idempotent replay returns the first response; key reuse with different payload fails; in-progress reservation survives process restart. Test retry after file transfer/render failure without duplicate issue/supersession. Never hold DB locks throughout network/render work.

## 10. Auth, roles and workflow security

Test correct/invalid login, access expiry, inactive user, cookie flags/CSRF/Origin, token rotation/replay-family revocation, logout/logout-all/password reset, owned session revocation and no token leakage. Revoked grants take effect even with an unexpired JWT.

Test each seeded permission set; GLOBAL ADMIN cannot read lab regulatory data or approve by default. ADMIN plus explicit lab APPROVING_OFFICER may approve only with author-independence. Role grants in Lab A never grant Lab B rights. Reviewer must not be an observation author; approver must not be initiator/author. Direct API calls fail despite hidden UI controls.

End-to-end: configure/confirm/start → valid test results → construction/checklist → submit → technical approve → final approve → generate → issue. Run both COMPLIANT and NONCOMPLIANT complete scenarios. Under-review edits fail; bounded return/reopen unlocks only named fields; changes append review invalidation; resubmission requires fresh review. Approved/issued correction creates a linked session/report revision; rejection/cancellation retain history.

## 11. Reports and storage

Test unofficial preview on unfinished/TODO data: watermark, no official number and no issue action. Test official immutable report_context_snapshot from approved current data; all 17 sections, references, equipment/environment, failures, N/A, approvals and retest history appear in both PDF/DOCX.

Structured context golden tests verify semantic equivalence and independence from later lab/manufacturer/user/equipment/rule master edits, including edits between final approval and first generation. Final approval must capture session_approval_snapshot before those masters can affect a report. Both renderers use stored values; no compliance calls from reporting. Verify context/file/manifest hashes are nonrecursive and correct, intended issuer/planned date mismatches block issue, renderer partial failure keeps UNISSUED, and revisions preserve old issued bytes. External edited DOCX cannot replace a canonical artifact.

Storage tests: MIME/size/actual bytes/hash, upload ownership, invalid filename/path, expired presign, cross-lab target/download, finalized object immutability, protected attachment/link deletion, orphan cleanup and worker retry. Private object versions used by issued context remain available through backup/restore.

## 12. Audit ownership

For instrument/source/evaluation/selection/correction/review/approval/issue/rule actions, assert exactly the owning service's transactional event with actor, scope, revision and correlation ID. Failed regulatory transactions leave no false success event. Auth failures/replay and report-worker failures have attributable durable events without credentials. Append-only events/approvals/results cannot be altered through application credentials.

## 13. Performance, CI and release gates

Smoke-test paginated 1000-report repository, all-17-section dashboard, large checklist/result history and no N+1 queries. Recommended coverage targets remain calculations 95%+, evaluators 90%+, services/overall backend 80%+; coverage cannot replace verified golden cases.

Required backend commands when present: ruff check ., ruff format --check ., pytest. Optional mypy. Frontend lint/build and appropriate tests apply from its implementation phases. Each phase reports commands/results and unresolved gates.

Phase 0 requires startup/health/toolchain tests only; it does not require implementing later auth or regulations. Each evaluator requires domain/procedure/applicability/boundary/pass/fail/reference tests before integration. Official release additionally requires verified applicable regulatory rules and passing workflow/migration/authorization/concurrency/report-context/render tests. A green synthetic fixture suite never waives TODO_REGULATORY_VALIDATION.
